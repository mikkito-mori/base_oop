# 1 Анализ, проектирование и инкапсуляция

## 📖 Контекст задачи (легенда)
Вы — начинающий разработчик в команде, которая делает учётную систему для университетской библиотеки. Заказчик (библиотекарь) описал, как работает библиотека сейчас — «на бумаге». Ваша задача — перенести эту логику в код.

## Описание предметной области от заказчика
«У нас есть книги. У каждой книги есть ISBN (уникальный номер), автор и название. Книга может быть либо на полке, либо выдана читателю — одновременно она не может быть в двух местах.

Есть читатели. Мы их пока не различаем — просто люди, которые берут книги.

Когда читатель берёт книгу, мы фиксируем, что книга теперь у него. Когда возвращает — книга снова доступна.

Важно: если книга уже выдана, мы не можем выдать её ещё раз — это ошибка, которую нужно явно показать.

Ещё нам нужно уметь посмотреть список всех книг и понять, какие сейчас доступны, а какие выданы.»

2. Проектирование классов (UML-эскиз)
Задача: превратить анализ в структуру классов и определить границы инкапсуляции.

Что сделать:

- Нарисовать UML-диаграмму классов (от руки + PlantUML). На этом этапе — минимум 2 класса: Book и Library. Класс User пока можно не вводить — но если вы чувствуете, что без него логика «провисает», зафиксируйте это как открытый вопрос.

Для каждого класса указать:

- атрибуты с типами;

- методы с сигнатурами (имя, параметры, возвращаемое значение);

- модификатор доступа для каждого атрибута и метода: + (публичный) или - (внутренний).

Письменно ответить на три вопроса (по 2–4 предложения каждый):

- Вопрос 1. Какие атрибуты Book должны быть неизменяемыми после создания? Почему?
- Вопрос 2. Где должно храниться состояние «книга выдана / доступна» — в классе Book или в классе Library? Обоснуйте.
- Вопрос 3. Какие методы Library должны быть публичными, а какие — внутренними (вспомогательными)? Приведите пример метода, который не должен быть публичным, и объясните, что может пойти не так, если его сделать публичным.
